# Stage 4 RFQ surface brief

- **Reviewer disposition:** `ship`. The completed surface is `/request-a-quote/`; it supersedes the Stage 3 RFQ preview/no-send state without claiming that production email delivery is publicly deployed or verified.
- **UI refresh approval and evidence:** The user explicitly approved the homepage and Products UI previews in `.impeccable/review/ui-refresh-preview/` and authorized extending their design rules to the RFQ and remaining routes. The authorized implementation is complete without repeat confirmation. Current RFQ desktop/mobile captures are `.impeccable/review/ui-refresh-result/request-a-quote-1440.png` and `request-a-quote-390.png`; layout and browser records accompany them. They verify the local implementation's UI, not live delivery.
- **Historical Stage 4 verification evidence:** Desktop CUA visual inspection completed. The Astro build completed with 0 errors and 0 warnings; Worker TypeScript passed; Vitest passed 18/18; the Cloudflare deployment dry run succeeded; and a local end-to-end `POST /api/rfq` returned `201` with Wrangler's simulated `send_email` output. No real email was sent. These earlier checks are not current UI-refresh validation.
- **Browser verification caveat:** The in-app browser could not load the third-party Turnstile iframe. The surface responded with the designed explicit load-failure message and visible invalid state rather than hiding the failure or implying that bot protection had passed.
- **Scope and mode:** Operate mode for an industrial buyer preparing one complete inquiry. Stage 4 validates and attempts delivery of one grouped email; it does not introduce an inquiry database, file upload, attachment storage, account, or CRM workflow.
- **Topology and typography:** H1 `Request a Fan Quote` introduces a compact header whose title and existing boundary aside align closely. Use the shared interior display scale `clamp(44px, 4.5vw, 64px)`, line-height 1, an 18-24ch measure, and 44px mobile H1s. The full form remains the primary column in a two-column desktop workspace; the sticky secondary guidance rail explains field checking, Turnstile verification, the email attempt, and the no-database/no-upload boundary. Remaining factual copy is unchanged.
- **Approved frame and density:** Align header, workspace, and footer to the 1440px content measure; desktop gutters are `max(32px, calc((100vw - 1440px) / 2))` and mobile gutters are 18px. Standard section spacing is 40-64px desktop and 28-40px mobile, with a 32px mobile default; breadcrumb bottom spacing is 24px desktop and 20px mobile. Compact header, workspace, form-heading, and group-transition gaps while retaining readable labels, helpers, errors, and persistent 52px-minimum controls.
- **Field groups:** Buyer and contact, product and delivery, requirement summary, conditional selection-help details, and review/submit. Persistent labels identify every control; required/optional indicators, readable helpers, dedicated error slots, and placeholders that supplement rather than replace labels remain visible and associated with their fields.
- **Contact and conditional rules:** At least one reply path, email or WhatsApp, is required. Preferred contact is a separate optional field. Choosing `Need selection help` reveals the operating-duty fieldset and makes application required; the extra fields are hidden and disabled for a selected product category.
- **Interaction and accessibility states:** The flow exposes visible pending, success, and failure states. Pending and failure copy appears through the form's `aria-live` output; the visible success state appears on `/thank-you/` only after a `201` and the tab-local marker. Submission disables the button, marks the form busy, changes its label, and locks duplicate clicks while validation and delivery are in flight. Invalid fields receive persistent copy and `aria-invalid`, and focus moves to the first invalid control.
- **Invalid-focus correction:** The UI pass also fixes a pre-existing empty-submit defect by collecting native invalid `input`, `select`, and `textarea` controls only, rather than marking invalid fieldsets. The focused retest reached `#customer-type`, showed 11 field errors, retained the entered name, found zero invalid fieldsets, and made zero API requests. Existing field names, conditional behavior, validation rules, submission states, and backend/delivery semantics are unchanged.
- **Turnstile treatment:** Bot protection is a visible labelled group with a loading message, keyboard focus treatment, invalid styling, and explicit missing, expired, verification, and script/iframe load-failure errors. Client feedback is immediate, but server verification of token, action, and hostname remains authoritative.
- **Server boundary:** The Worker accepts same-origin JSON only, applies a bounded request size and server-side field validation, verifies privacy acknowledgement and Turnstile, and attempts one grouped email only after those checks pass. Delivery failure never becomes a success state, and the form preserves the buyer's entries for correction or retry.
- **Success truth:** `/thank-you/` confirms delivery only when the same browser tab holds the `sessionStorage` delivery marker written after the successful API response. Direct navigation to that route shows an unconfirmed state and is never evidence that an email was sent.
- **Responsive behavior:** The desktop form and sticky rail reflow to one column at 1020px, where the rail becomes static. At 720px, the header, all two-up field grids, guidance content, submit row, and actions use one-column order with 18px gutters; Turnstile can scroll horizontally rather than clipping. Current desktop/mobile captures and site layout checks include RFQ widths down to 320px, with no measured overflow, clipping, or image-load defects and all visible RFQ controls at least 52px high.
- **Current implementation validation:** The 2026-09-15 16:49 build passed with 23 Astro files, zero errors/warnings/hints, and 14 routes; Worker TypeScript, 63 Vitest tests, and 12 Node CI tests passed. The site recorded 81 layout checks. Browser `regression.json` retains the original 19-pass / 1-failure record; passing `focused-regression.json` closes the invalid-focus scenario, so combined evidence verifies all 20 groups. RFQ conditionals, entry preservation, invalid/pending/failure/success UI, status-route confirmation, and control sizes were exercised with locally mocked API/Turnstile responses. No live Siteverify, email acceptance, or inbox delivery was tested by these UI checks.
- **Detector review limitation:** One mechanical pass was reviewed manually. Its saved `ui-refresh-result/design-detection.log` output is truncated, preventing a reliable complete count or clean claim. An existing RFQ error-summary left-border warning and mainly existing color/size/radius documentation advisories were reviewed; no unrelated backend, factual-content, or error-treatment changes were made to suppress them.
- **Local-test truth:** Local mode uses Cloudflare's public always-pass Turnstile site key and secret with localhost-only hostname configuration. Wrangler's local `send_email` binding writes simulated output; a local `201` proves the tested pipeline reached that simulator, not that a real recipient received mail.
- **Live-mode boundary and remaining external setup:** The production hostname, live Turnstile widget, verified email destination, restricted sender and Worker Runtime Secrets are prepared. Launch still requires the GitHub-backed production build, public-domain binding, a live-domain end-to-end delivery check, and approval of the final privacy and mailbox-retention process. Test keys, localhost hostnames, placeholder addresses, missing server secrets or an unverified delivery result must fail closed and must not be described as live delivery.
